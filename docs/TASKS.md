# RoutForge — Backlog dei task

*Ordine = dipendenze (CONTESTO §6). Ogni task è piccolo, ha spec e scenari, produce qualcosa di verificabile con `npm run verify`. Stati: `aperto` · `in corso` · `fatto` · `bloccato`. Marcatori: **M** = delegabile a un agente meccanico (OpenCode); **R** = rischioso → snapshot prima; **CPn** = checkpoint prima di iniziare.*

**Colonna Modello** (piano Max; decisione D-MODEL-1 del 23/09/2026): **Fable 5.1** = T-000, lettura di contesto lungo e decisione irreversibile · **Fable 5.1 (piano) → Opus 5.5 (codice)** = T-013, T-019, T-033: il piano si scrive con Fable in `docs/piani/<ID>.md`, il codice con Opus seguendo quel piano · **Opus 5.5** = task difficili (casi limite, rischio dati, codice nativo) · **Sonnet 5** = default per funzionalità e UI · **Haiku 4.5** = regole chiare e meccaniche. Escalation se il gate resta rosso dopo due tentativi: Haiku → Sonnet → Opus 5.5 → Opus 5.5 con sforzo più alto → Fable 5.1. Fable consuma più in fretta i limiti settimanali (al massimo il 50% sul piano Max): usalo solo dove indicato.

`/task next` prende il primo `aperto` con dipendenze `fatto`. L'hook SessionStart mostra i primi cinque.

## Regole per aggiungere task
Un task nuovo nasce da uno scenario o da un paragrafo di spec non ancora coperto; mai da un'idea non scritta nelle spec. Se un task supera ~300 righe di diff, va spezzato.
